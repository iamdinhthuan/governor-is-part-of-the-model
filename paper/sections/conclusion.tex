\section{Threats to validity}
\label{sec:threats}

\textbf{Internal validity.}
Scheduling variants give byte-identical predictions, so accuracy is
not a confound. Run order was rotated, the page cache was warmed before
each phase, and clock state was stored, restored and verified. Thermal state was controlled with 10\,s pauses and
junction-temperature logging. The Jetson peaked at
67.4\,$^\circ$C in application runs and 69.2\,$^\circ$C under
\texttt{trtexec}, far from throttling. The Rubik CPU runs, by contrast,
sit at the 95\,$^\circ$C thermal limit and show a 17\% drift
(\cref{sec:rubik}). Repeats per cell are few, and 20\,Hz power and
clock sampling cannot resolve sub-50\,ms clock changes
(\cref{sec:diagnosis}). A direct devfreq lock of the memory (EMC) clock
did not hold on this release, a silent failure also reported on this
board family~\cite{kang2026emc}. In the fixed-frequency sweep it was
therefore logged and its influence bounded to 2\% of the fitted slope. \texttt{jetson\_clocks} does hold it
(\cref{sec:setup}), so locked-versus-default comparisons include any
memory-clock effect. Runs last 9--203\,s on the Jetson and
${\approx}26$\,min for the Rubik CPU sweep, so deployment-length steady state
was not tested. The ramp in \cref{fig:traces} shows that a run's first
seconds differ from the rest. The Ultralytics baseline uses its
own engine export. Its AP agrees to $3\times10^{-5}$, but engine
tactics may differ slightly.

\textbf{Construct validity.}
\texttt{VDD\_IN} is the module's main input rail. It excludes
carrier-board loads (fan, USB peripherals, storage regulators) but
overstates the energy of the SoC compute rails alone.
The idle cost of locking clocks includes the higher memory, CPU and
GPU clocks. The on-board sensor was not validated against
an external meter, so comparisons rely on its run-to-run
consistency, not its absolute accuracy. Latency starts when a
JPEG file is available, so it includes decode but not camera capture,
ISP processing or output transmission. Process CPU time
includes all threads.

\textbf{External validity.}
The main study uses one Jetson Orin Nano Super and one software stack,
only partially offset by the replications of \cref{sec:crossplatform}. Other Jetson modules, power modes, JetPack releases, hardware
JPEG decode~\cite{chen2026nvjpeg} or DeepStream pipelines may shift the
magnitudes, and other vendors' governors may differ. Pi~5
energies cover the SoC only, because the Hailo-8 sits on the unmonitored
5\,V rail. Its on-chip NMS uses a 0.2 score threshold, so Pi accuracy is
not comparable with the other boards. The Rubik Pi~3 has no usable power
sensor. Its NPU stack uses a third-party runtime
(\texttt{qai-appbuilder}) rather than the vendor SDK. Its INT8 model
ends in the standard head with host-side NMS, so accuracy is not comparable with the float
stacks (\cref{sec:rubikhtp}). That userspace wedged under concurrent
calls, so the NPU pipeline serializes accelerator calls and overlaps
only host stages. Multi-threaded CPU inference emits rows in
nondeterministic order, so prediction equivalence there is shown on
sorted rows (identical in all 24 ladder cells), not by a byte-level
hash. The pipelines are
written in Python; native C++ or DeepStream would shorten the
host stages and could reach the GPU-bound regime with fewer decode
workers. Batch size was 1 throughout, as in a camera application;
its known interaction with GPU frequency~\cite{nabavinejad2022batching}
was not measured. The compression screening (one seed, short recovery,
\texttt{opt0} builds) is evidence about that budget, not a
general verdict on pruning or quantization.

\section{Conclusion}
\label{sec:conclusion}

On an embedded GPU, the deployed cost of an NMS-free detector is not a
property of the model alone. Under the stock governor, the same
YOLO26n engine costs 4.2\,ms or 13.2\,ms depending on how busy the
application keeps the GPU. A simple duty-cycle model describes this
behavior. Restructuring only the host pipeline, under default governors
and at unchanged accuracy, gave $2.4\times$ the throughput of the best
sequential pipeline at locked maximum clocks.

The CPU governor is part of the same loop. On the sequential and
prefetch schedules, a sleeping CUDA wait lets it lower the host clock
and, through slower submission, the GPU clock. A per-task utilization
clamp recovers most of this loss without busy-spinning. On the full
two-worker pipeline the wait policy costs nothing under default and
locked clocks. Only the stream-synchronization boundary still costs
24\%.

Below capacity, idle power sets energy per frame and the schedule sets
latency. Near capacity the schedule decides energy again, so
the right schedule depends on the arrival rate. Model-level decisions
matter much less in an optimized pipeline. A lower input resolution gave
$27$\% more throughput in the naive pipeline but only $2$--$4$\% in the
optimized one ($6$--$10$\% with the garbage collector disabled).
Compression and routing gained less than scheduling.

The effect transfers to a Raspberry Pi~5 with a Hailo-8 NPU and to a
Qualcomm board, but its mechanism moves to the host. The Hailo-8
exposes no frequency control, the Qualcomm CPU stack is bound by thermal
management, and on its Hexagon NPU the scheduler down-clocks the core
that feeds the accelerator. Edge-detection efficiency should thus
be reported for the whole pipeline under deployment governors.
